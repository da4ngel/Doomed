# Evaluation — metric definitions

**Definitions come first, implementation second.** Written before `eval/metrics.py` exists,
deliberately: a metric written after reading the retriever tends to measure what the
retriever already does well. If the numbers in this project are to mean anything, the
definition has to be able to embarrass the implementation.

Every metric below is defined against the hand-authored gold sets in `eval/suites/`. No
gold label was generated by a model — grading a retriever with our own generator would be
circular, and the dev set ships no answers at all, so this was always hand work.

---

## 1. Retrieval metrics

Let **G** be the set of gold documents for a question and **R@k** the ranked list of
documents in the top *k* retrieved chunks (deduplicated by `doc_id`, because two chunks
from the same document are one document found).

### `recall@k`

```
recall@k = |G ∩ R@k| / |G|
```

Averaged over questions. The standard measure: did we find the relevant material.

### `precision@k`

```
precision@k = |G ∩ R@k| / k
```

Reported but not optimised. With `|G|` often 1–3 and `k = 10`, precision is bounded low by
construction, so it is diagnostic rather than a target.

### `coverage@k` — **the metric that proves sub-track 1B**

```
coverage@k = fraction of questions where G ⊆ R@k
```

**Recall rewards finding *a* relevant document; a multi-hop question needs *all* of them.**
A question whose answer requires three documents scores `recall@10 = 0.67` when two are
found — which sounds like partial success but is a wrong answer. `coverage@k` is binary
per question: either every gold document is present or the question is unanswerable from
that context.

This is the metric worth inventing for this problem, and it is the one that separates the
hybrid+graph configuration from plain hybrid in the ablation.

### `nDCG@10`

```
DCG@k  = Σᵢ  relᵢ / log₂(i + 1)          for i = 1..k, relᵢ ∈ {0, 1}
IDCG@k = DCG of the ideal ranking (all gold first)
nDCG@k = DCG@k / IDCG@k
```

Rank-sensitive, so it separates "found it at rank 1" from "found it at rank 9" — which
matters because the composer sees a truncated context, not the whole list.

### `MRR`

```
MRR = mean over questions of  1 / rank(first gold document)   (0 if none in top k)
```

### `first_relevant_rank`

The raw rank of the first gold document, reported as a distribution rather than a mean.
A mean hides the bimodality: retrieval usually hits at rank 1 or misses entirely.

## 2. Answer metrics

### `groundedness`

```
groundedness = count(claims where support != "inferred") / count(claims)
```

**Computed, not judged.** This is why `claims[]` with per-claim `citation_ids` had to be
frozen on day zero — it cannot be retrofitted onto a composer that returns prose. A
refusal with zero claims scores 0.0 and must not raise.

### `citation_precision` / `citation_recall`

```
citation_precision = cited documents that are gold / cited documents
citation_recall    = cited documents that are gold / gold documents
```

Precision catches the failure this corpus punishes hardest: a citation that is real,
resolvable, and attached to the wrong claim.

### `correctness` (0–3, LLM judge + human spot-check)

| Score | Meaning |
|---|---|
| 3 | matches gold, correctly grounded |
| 2 | substantially correct, minor omission |
| 1 | partially correct or hedged past usefulness |
| 0 | wrong, or fabricated |

The judge is itself validated: 20 questions are human-rated and the agreement percentage
is reported. Almost no team validates their own evaluator, and reporting the agreement
pre-empts the obvious challenge to every number that depends on it.

### `refusal_accuracy` and false-refusal rate

```
refusal_accuracy   = correctly refused / questions that are genuinely unanswerable
false_refusal_rate = refused / questions that are answerable
```

Both are needed. A system that refuses everything scores 1.0 on the first alone.

## 3. Multimodal metrics (sub-track 1A)

### `asset_precision` / `asset_recall`

```
asset_precision = returned assets that are gold / returned assets
asset_recall    = returned assets that are gold / gold assets
```

Assets are compared **by content hash, not by path**: `images/plate_01.png` and
`codex/images/plate_01.png` are byte-identical, and counting them as two would inflate
recall while making precision meaningless.

Precision matters more than it looks. Attaching every retrieved image scores well on
recall and destroys precision, and a wall of irrelevant figures is a worse answer than
none.

### `gold_recovery` — the 1A pipeline metric

```
gold_recovery = questions whose gold answer appears in its image's description / questions
```

Measured on the image index directly, before any retrieval or composition. It isolates
whether the *extraction* worked from whether the *answer* did. Currently **11/11**.

### `chart_binding` — the trap metric

```
For each chart case: the value bound to the plate's SUBJECT label
                     equals the gold value, AND is not any forbidden value.
```

Not "the answer appears somewhere in the description". `plate_07` prints 55 twice — once
as the Lantern's attunement cost and once as an Adept-tolerance reference bar — so only
label binding distinguishes a correct read from a lucky one.

## 4. Agentic metrics (sub-track 1C)

### `success@budget`

Fraction of questions answered correctly within the step budget (6 steps).

### `avg_steps`

Mean steps taken. Reported beside `success@budget`: a system that always takes 6 steps and
one that averages 2 can score identically while costing three times as much.

### `redundancy_rate`

```
redundancy_rate = near-duplicate queries issued / total queries issued
```

Two queries are near-duplicates when their embeddings exceed a cosine threshold. This is
the churn measure — a loop that rephrases rather than reasons scores high.

### `gain_per_step` — **the metric that proves the loop reasons**

```
gain_per_step[i] = new gold documents first seen at step i
```

A loop that churns returns zeros after step 1. A loop that reasons keeps finding documents
it could not have reached without what the previous step taught it. Reported as the
sequence, not a mean — `[3, 2, 0]` and `[2, 1, 2]` have the same mean and tell different
stories.

---

## 5. System metrics

`p50` / `p95 latency`, `cost_usd/query`, `tokens/query`, `cache_hit_rate`, `429 rate`.

A cache hit counts as a call. Excluding hits would shrink the denominator and make
`cache_hit_rate` meaningless.

## 6. Failure taxonomy

Every miss is labelled. **Reporting the split is the point** — most teams conflate the
first two and then optimise the wrong layer.

| Label | Meaning | Fix lives in |
|---|---|---|
| `extraction` | the fact never left the document | ingestion / OCR / VLM |
| `retrieval` | the gold chunk was not in top-k | index / fusion / rerank |
| `synthesis` | the gold chunk *was* in context, answer still wrong | prompt / composer |
| `refusal` | refused an answerable question, or answered an unanswerable one | critic / verifier |

The distinction is mechanical, not a judgement call: if the gold chunk is absent from the
retrieved context it is `retrieval`; if present and the answer is wrong it is `synthesis`.

## 7. The ablation table

Every row is one configuration of one retrieval function, never a second
implementation — otherwise a row measures two changes at once.

Filled numbers live in **`docs/reports/ablation.md`**; this table records what each row
is for and whether it has run.

| # | Config | status |
|---|---|---|
| 1 | BM25 only | run |
| 2 | Dense only | run |
| 3 | Hybrid RRF | run |
| 4 | Hybrid + rerank | run — **worse on multi-hop**, coverage 0.429 -> 0.143 |
| 5 | + section expansion | run — **worse everywhere**, 0.429 -> 0.286 |
| 6 | + graph expansion (1B) | run — **best row**, 0.429 -> 0.714 at 20 ms |
| 7 | + both expansions | run — worse than 6 alone; they compete for one budget |
| 8 | + conflict layer | blocked: A4 exists, no answer path consumes it yet |
| 9 | chunk 300 / 450 / 600 sweep | `scripts/chunk_sweep.py`, isolated indexes |
| — | + agentic loop (1C) | blocked: P2's orchestrator |

The answer-side columns originally planned here — `grounded`, `correct`, failure split,
$/q — are deliberately absent rather than blank. Nothing produces a real answer yet, so
every one of them would be a synthetic number in a table a reader would take as measured.

Rows 5-7 spend the same k as row 3: expansion evicts the weakest base hits rather than
extending the list (ADR-009). Appending would make row 6 unable to lose and credit the
graph for what is really just more evidence.

Row 9 is a sweep rather than a config: chunk size is derived from the embedding model's
512-token context (ADR-008), and the 600 row is expected to lose recall because 8.8% of
its chunks were silently truncated at embed time. It builds into throwaway indexes and
its own Qdrant collection, so it never risks the index the API is serving.

## 8. Regression gate

**Implemented** as `uv run python -m eval.runner --suite all --ablation --gate`
(`make gate`). It scores every suite under every retrieval config and exits 1 if any
gated metric fell below `eval/baseline.json`.

Gated: `recall@k`, `coverage@k`, `ndcg@k`, `mrr` - on every config, not just the
default, because a change that helps the default and quietly breaks `sparse` is still a
change we want to see.

**Not gated: latency.** It is a property of the machine the run happened on, and a gate
that fails on a busy laptop is a gate somebody disables the week before the deadline.

**Tolerance is 0.001, not the 3 points originally specified here.** Retrieval scoring is
deterministic - same index, same query, same ranks - so a number that moves means
behaviour changed, and the wide band would have hidden exactly the regressions worth
catching. The band was written before we knew the run was reproducible; it is now,
byte-for-byte across two full runs. Answer-level metrics are stochastic and will need
their own wider band when A5/A6 land, at which point this section gets a second row
rather than a looser number.

A gain is reported, not failed - and it is the moment to re-record:
`make record-baseline`, committed **with** the change that moved the number, so the diff
shows the cause and the effect together.

The baseline recorded 2026-09-06 (UTC) is the ablation in `docs/reports/ablation.md`.

## 9. What we expect to fail, and will report

`docs/limitations.md` records these with numbers as they are measured, not on D5 from
memory. **Written 2026-09-06 (UTC)** - it now carries the rerank result, the 0.429
coverage ceiling, the unmeasured answer layer and the seven abandoned approaches with
the number that killed each:

- chunk size sweep — what won and by how much. **Not run.** 450 was set from the embedder's context window after 600 silently truncated 8.8% of chunks (ADR-008), which is a defect argument, not a comparison
- naive top-k without rerank on multi-hop specifically - **measured: rerank COSTS us here.** 1B coverage@10 0.429 -> 0.143, recall 0.714 -> 0.500, while 1A nDCG 0.715 -> 0.779. Rerank belongs behind the intent router, not on by default
- Tesseract on the plates, against the VLM (`scripts/ocr_vs_vlm.py`)
- the agent loop without the redundancy guard — the churn rate measured, then fixed
- any approach abandoned, with the number that killed it
